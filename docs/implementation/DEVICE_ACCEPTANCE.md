# 真机验收与安全迁移

本文件是待执行的验收清单，不是已经通过的测试报告。

## 当前已知能力限制

CarrierConfig 重置会实际调用删除覆盖接口并读取当前状态，但接口会吞掉部分远程失败、内部处理异步，合并后的配置也不包含覆盖来源。当前代码不能独立证明删除完成，因此明确返回「已请求但尚未确认」、保留恢复保护并暂停自动恢复，不写成功重置历史。全卡操作可能在第一张未确认卡后停止。读取当前状态可以用于安全核对，但不能把它说成已证明恢复运营商默认值。必须在后续平台/真机研究取得可靠证据后再开放成功判定。

## 安装前

每次 Release 提供 `tensor`（`app.mystery0.ims.tensor`）与 `legacy`（`io.github.vvb2060.ims`）两个 APK，每个都包含完整官方/私有内置双模式。namespace 和第一方组件类名统一为 `app.mystery0.ims.tensor`，应用身份和私有数据按 applicationId 隔离。

### 保留旧应用身份：安装 legacy
1. 保留旧版及其数据，先关闭自动恢复，等待旧版特权操作完成；保存待核对的配置与恢复状态。
2. 核对原安装与待安装 APK 的签名证书 SHA-256，并确认新 APK 的 `versionCode` 更高。只有签名一致且版本更高时才可按本方案覆盖升级；CI 两包使用同一组 Secrets 不等于已核实旧版证书。签名不同则停止，不要卸载旧版来绕过检查。
3. 覆盖升级 `io.github.vvb2060.ims`，不得清理应用数据、重命名配置键或删除私有 `noBackupFilesDir` 原值备份。`sim_config_<subId>`、`auto_restore` 及 `persistent_volte_<subId>.json` 继续原地保留。
4. 升级后明确选择后端，先只读核对历史、自动恢复开关及原值恢复能力；确认前保持自动恢复关闭。不能以构建成功代替升级保留数据的真机证据。

### 独立安装新应用：安装 tensor
1. 保留旧版 TensorIMS 和它的数据，先关闭旧版自动恢复。
2. 在旧版内恢复已修改 SIM 的持久化 VoLTE 原始值；暂未激活的 SIM 需要重新激活后恢复，不要先删除其恢复备份。
3. 确认原值恢复后安装 `app.mystery0.ims.tensor`；它不覆盖 `io.github.vvb2060.ims`，不读取旧包私有目录，也不自动迁移数据。
4. 新包首次明确选择官方或内置模式，先读取当前配置，再决定是否写入。新包首次使用持久化 VoLTE 时建立自己的恢复备份。
5. 两包不可同时启用自动恢复修改同一 SIM；验证新包恢复功能前，不卸载旧版或清理其数据。两包的进程内操作锁不能保证跨包或 Android 全局 shell 委托并发安全。

## 双包构建、安装与升级验收

以下检查分别记录两个 flavor，不以一包通过替代另一包；全部仍待执行。

- [ ] 同一 Release 含两个同 `versionCode`/`versionName` 的 release APK，及各自对应的 mapping；文件名含 applicationId，四个文件不相互覆盖
- [ ] 两 APK 签名与预期发布证书一致；另行核对旧安装的证书与 versionCode，不把 CI 配置相同当作旧证书已确认
- [ ] 两包与官方 Shizuku 可同时安装，无 Provider authority 或权限名冲突；每包 Instrumentation 均指向自身应用身份和统一 namespace 的正确类
- [ ] `legacy` 在满足签名/版本前提下覆盖旧安装后，历史、自动恢复数据、SIM 身份校验及私有 VoLTE 原值备份仍可读取和使用
- [ ] `tensor` 独立安装不读取、迁移或清理 legacy 数据；两包的配对身份、会话和私有服务不会串用
- [ ] 每包分别完成下列 OFFICIAL、EMBEDDED 验收矩阵；仅逐包进行写入，保持另一包自动恢复关闭
