# 无线 ADB 通知配对验收

## 流程与安全边界

- 内置模式中点击「通知配对」，按需允许通知；Android 17（目标 API 37）还需本地网络发现权限。
- 前台通知建立后才打开开发者选项。用户开启「无线调试」，手动点击「使用配对码配对设备」。
- 保持系统配对对话框可见，下拉通知并在通知的直接回复框输入 6 位配对码。进行中的通知本体不打开应用，不申请悬浮窗权限。
- `_adb-tls-pairing._tcp` 与 `_adb-tls-connect._tcp` 独立查找。配对码提交时重新发现配对端口，配对成功再发现连接端口。
- 只接受回环或当前设备网卡上的 NSD 地址，实际 TCP 连接仍强制 `127.0.0.1`。多个不同本机端口产生歧义时拒绝猜测。
- 已配对后可点击「重新连接」，重新发现当前端口。不会使用官方 Shizuku 的身份、配置或管理器权限，不会自动切换模式。
- 前台流程最长 150 秒，结束、取消、模式变化与进程销毁时回收发现和传输；旧通知/重复回复不能启动新配对。配对码不进入 Bundle 保存状态、首选项或日志。

## 云端与设备验收的区别

云端 JVM 测试可验证帧、阶段、错误处理、发现队列、服务丢失/迟到回调、取消和通知回复门禁；双 flavor 构建与 R8 检查验证打包。这些都不等同于 Android Conscrypt、JNI、真实 adbd、系统通知与 Binder 启动链路通过。

真实验收必须在 Android 13+ 且支持 arm64-v8a 的设备/模拟器进行。仅 x86_64 ABI 的模拟器不能装载现有 ARM64 JNI 配对库；缺少无线调试设置或本机 mDNS 服务的模拟器也不能替代真实配对验收。

## 必测矩阵

1. 两 flavor 分别新配对：不输入任何端口，不切回应用，通知输入有效码后自动连接并显示已认证私有 Binder。
2. Android 13、14+ 与 Android 17：通知拒绝、通知渠道关闭、API 37 本地网络权限拒绝及重新授权。
3. 故意错误验证码后保留设置页，从同一通知重试；配对对话框关闭重开后端口改变，旧通知不能误连旧端口。
4. 搜索、等待码、配对、连接各阶段取消；后台杀进程再点旧通知；快速重复点击回复。
5. 超时、Wi-Fi 中断、无线调试关闭重开、连接端口变更；发现周围其他设备时不连接它们。
6. 配对已成功但启动失败时，显示分阶段诊断，可单独重连，不声称成功。
7. 外置模式正常使用、拒绝外置授权、切换门禁、恢复阻塞保持原有语义；两包的私有桥接身份彼此隔离。
8. 对最终签名且混淆的 release APK 再验收；debug 成功不能证明 R8/release 与既有安装签名兼容。

## 用户运行的 Windows 助手

运行 `scripts/test-wireless-adb-emulator.ps1 -ApkPath <测试 APK 绝对路径> -Serial <adb devices 中设备序号> -Flavor tensor`；旧包 flavor 使用 `legacy`。

脚本只使用已有 adb/运行中的设备；安装前确认，使用 `adb install -r`，签名不匹配即停止，绝不卸载、清数据、擦模拟器或修改系统 ADB 设置。验收仍由用户操作系统设置与通知。日志只收集本应用选定诊断标签，不收集或传输配对码；结果留在本机，用户核对后再分享。
